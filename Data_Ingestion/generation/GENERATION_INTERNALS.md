# Section Generation — GenAI Internals

A deep, code-referenced walkthrough of **how one document section is generated**:
what context is assembled, where every piece comes from, how instructions and the
source document flow into the prompt, and how the LLM is called.

> Model: **Gemini 2.5 Flash** on **Google Vertex AI**, via `litellm`.
> All file paths below are under `Data_Ingestion/`.

> **⚠️ UPDATE — single source of truth is now the template JSON.**
> The Excel (`mapping_source.xlsx`) and the compiler (`compile_mapping.py`) have
> been **removed**. Every section's spec (`instructions`, `scope_boundary`,
> `variables`, `format`, `depth`, `source_fields`, `annexure`) now lives **inline
> inside `templates/<doc>.json`**, and `build_section_guidance` reads it from the
> section dict passed by the generator (no `section_specs.json` lookup). Where this
> document mentions "Excel Description", "compile", or "section_specs.json", read
> it as historical context — the *content* is now hand-edited in the template JSON
> and picked up on server restart. See `mapping_data/TUNING_GUIDE.md`.

---

## 0. The 30-second summary

Each section is generated by **one LLM call** whose prompt is assembled from five
independent sources, then persisted as a `SectionVersion`:

```
                         ┌─────────────────────────── SYSTEM PROMPT ───────────────────────────┐
 1. Project fields  ───► │ role · project info · BUSINESS CONTEXT · PROJECT DESCRIPTION         │
 2. Source doc(s)   ───► │ SOURCE DOCUMENT CONTENT  (parsed text + Vision-AI image text + tables)│
 3. Ontology        ───► │ ORGANISATION CONTEXT · DOC-TYPE GUIDANCE · GLOSSARY · AESL SYSTEMS    │
 4. Prior sections  ───► │ SECTIONS ALREADY WRITTEN  (150-char previews, for coherence)          │
                         │ FORMATTING RULES · CONTENT QUALITY RULES                              │
                         └──────────────────────────────────────────────────────────────────────┘
                         ┌──────────────────────────── USER PROMPT ────────────────────────────┐
 5. Template + Excel ──► │ "Generate the <Section>" · SECTION INSTRUCTIONS (Excel Description)   │
                         │ ADANI TEMPLATE SPECIFICATION (MUST-NOT-INCLUDE · columns · depth …)   │
                         └──────────────────────────────────────────────────────────────────────┘
                                        │  combined → Gemini 2.5 Flash → Markdown
                                        ▼
                             SectionVersion (content, prompt, model)
```

## 2. Context is built in TWO layers

### Layer 1 — the shared *job* context (built once per document)
`_run_generation_job` calls `_load_job_context(job_id)` **once**, returning
`(llm_context, user_inputs, system_instructions)` that every section reuses.

**`_load_job_context` (`generation_service.py`)** does:

1. Read the job row → `document_id`, `user_inputs_json`, `template_id`, `document_type`.
2. Resolve the document id list: `all_doc_ids = user_inputs["document_ids"] or [document_id]`.
3. For **each** attached document:
   ```python
   meta   = store.get_meta_json(doc_id)                 # storage → parsed JSON
   parsed = ParsedDocument(**meta)                      # models/meta_schema.py
   ctx    = parsed.to_llm_context(max_chars=20_000)     # ← per-doc cap 20k chars
   contexts.append(f"=== Source Document: {parsed.source_filename} ===\n{ctx}")
   ```
4. Join docs, then **append the AI-derived analysis**:
   ```python
   llm_context = "\n\n---\n\n".join(contexts)
   derived_ctx = user_inputs.get("derived_context", "")  # "## AI-Derived Project Analysis…"
   if derived_ctx: llm_context += "\n\n---\n\n" + derived_ctx
   llm_context = llm_context[:60_000]                    # ← total cap 60k chars
   ```
5. Resolve `system_instructions` from the template (`template.system_instructions`).

So **Layer-1 context = [source doc(s) text] + [12 AI-derived fields]**, capped at 60k chars.

### Layer 2 — the per-section prompt (built for every section)
`generate_section` (`generator.py`) receives the Layer-1 `llm_context` and **re-caps it**:
```python
_MAX_CONTEXT_CHARS = 8_000                               # generator.py
if len(llm_context) > _MAX_CONTEXT_CHARS:
    llm_context = llm_context[:8_000] + "\n\n[... document truncated for brevity ...]"
```
> ⚠️ **Important nuance:** each section sees at most the **first 8 000 chars** of the
> Layer-1 context (source docs first, then derived analysis). For a small source doc
> (the Drishti BRD is ~4.3k chars) the whole doc fits and part of the derived analysis
> follows. For large inputs, later source pages and most of the derived block are
> truncated per section. **To feed sections more source/derived context, raise
> `_MAX_CONTEXT_CHARS`** (higher token cost per call). This is the single biggest
> context knob.

## 3. Where each `user_inputs` field comes from

`start_job_from_project` (`generation_service.py`) maps the DB Project/DerivedData onto
`user_inputs` — this is how form data enters generation:

| `user_inputs` key | Source (DB field) | Used in prompt as |
|---|---|---|
| `project_name` | `Project.project_name` | PROJECT INFORMATION |
| `document_type` | override / `Project.document_type` | resolves template + ontology |
| `business_problem` | `Project.problem_statement` | **BUSINESS CONTEXT** |
| `project_description` | `Project.proposed_solution` **or** `project_objective` | **PROJECT DESCRIPTION** |
| `expected_outcome` | `Project.project_objective` | (context) |
| `stakeholders` | `Project.stakeholders_json` → "Name (Designation)…" | PROJECT INFORMATION |
| `additional_instructions` | joined extra fields (BU, code, constraints, risks, tech landscape, pain points, deadline, timeline, cost…) | ADDITIONAL INSTRUCTIONS |
| `document_ids` | `Project.document_ids_json` | drives `_load_job_context` |
| `template_id` | `Project.template_id` | section resolution |
| `derived_context` | 12 `DerivedData` fields → `## AI-Derived Project Analysis` | appended to `llm_context` |

> This is why `proposed_solution` matters: it becomes **PROJECT DESCRIPTION**, the
> primary "what we're building" signal for every section.

## 4. How the SOURCE DOCUMENT becomes prompt text

`ParsedDocument.to_llm_context` (`models/meta_schema.py`) converts a parsed upload into
plain text the LLM can read. It walks every element **in page + reading order**
(`all_elements_by_page`) and renders:

- **Text** → `"{'#'*heading_level} {content}  <!-- text#txt_0007 -->"`
- **Image** → uses the **Vision-AI description** captured at upload time:
  ```
  [IMAGE [architecture_diagram]: <ai_description> Key components: SAP, SCADA, …]  <!-- image#img_0002 -->
  ```
  (`ai_description` / `image_type` / `key_elements` are filled by
  `parsers/vision_analyzer.py` during `storage.persist_all`, before base64 is dropped.)
- **Table** → the pre-rendered Markdown pipe table (`TableElement.markdown`).

Every element keeps its `ref` (`text#txt_0007`, `image#img_0002`, `table#tbl_0001`) as an
HTML comment, so content is traceable. The result is truncated to `max_chars`.

**Net effect:** diagrams and tables in the uploaded document are converted to text
(via Vision AI + Markdown) and become first-class source content in the prompt — the
generator never sees raw images, only their descriptions.

## 5. How INSTRUCTIONS flow (template → prompt)

There are **two complementary instruction streams**, deliberately non-overlapping:

### 5a. The section instruction (the "what to write")
Comes from the **template** `templates/<doc>.json`, whose `instructions` field is the
Excel **Description** (compiled by `mapping_data/compile_mapping.py`). `_run_generation_job`
reads it via `get_sections_for_job` → `cfg["instructions"]`, passes it to `generate_section`
as `section_instructions`, and it lands in the USER prompt template:

```python
# generator.py
_GENERATION_PROMPT = """Generate the **{section_title}** section.

SECTION INSTRUCTIONS:
{section_instructions}                      # ← Excel Description (via template)

{mapping_guidance_block}Write this section now. Start directly with the content…"""
```

### 5b. The spec block (the "how / boundaries")
`generate_section` calls `build_section_guidance(document_type, section_title)`
(`section_mapping.py`), which reads the spec fields from the **template section dict**
(passed by the generator as `section_spec`) and emits the
**complementary** spec — nothing repeats the Description:

```
## ADANI TEMPLATE SPECIFICATION (authoritative — follow exactly)
**MUST NOT INCLUDE (scope boundary):** proposed solutions, tools, or technology…
**Required columns / variables:** Req # | Description | Rationale | …
**Output format:** Table — first row MUST be a header row with exactly these columns…
**Depth:** Detailed — cover thoroughly with specifics, metrics and named systems.
**Generation notes:** Requirement IDs like FR-001…
**Source fields to pull from (project inputs):** Functional requirement, …
**Regulatory / annexure reference:** (NDPR only) …
```

This block is inserted as `{mapping_guidance_block}` in the USER prompt (5a).

> **Design rule:** the Description lives only in `section_instructions`; the boundary/
> columns/depth/sources live only in the guidance block. Same expert Excel, two slots,
> zero duplication.

### 5c. Document-wide style
`template.system_instructions` (generated per doc type by `compile_mapping.build_template`)
is prepended to the SYSTEM prompt as `## DOCUMENT STYLE INSTRUCTIONS`.

## 6. Business grounding (ontology)

`_build_system_prompt` calls `ontology.for_generation(document_type, scan_text)`
(`generation/ontology.py`). `scan_text` is a concatenation of project name, business
problem, description, additional instructions, derived context, and the (8k-capped)
source context. Ontology returns a **small, matched** block:

- `company_context` — Adani Group + the matched entity (AESL/AEML) + regulators.
- `document_context` — what this doc type IS at Adani (purpose, required inputs, position
  in the BRD→NDPR→NFA→NIT→RFP chain, reviewers, risk-if-weak).
- `glossary_block` — only glossary terms that literally appear in `scan_text`
  (word-boundary match; ≤35 terms).
- `tech_landscape_block` — only AESL systems mentioned in `scan_text` (≤10).

It never dumps whole files (549 terms / ~130 systems) — only per-call matches, hard-capped
to ~1k tokens. Loaded once via `@lru_cache`; degrades to `""` on any error.

---

## 7. Coherence across sections (prior-section previews)

`_run_generation_job` accumulates a `previous_sections` list. `_build_system_prompt`
renders each prior section as a **150-char preview** under `## SECTIONS ALREADY WRITTEN`:

```python
preview = s["content"][:150].strip() + ("…" if len(s["content"]) > 150 else "")
```

This gives the model just enough to avoid repetition without bloating the prompt — and is
why **wave-parallel generation stays coherent**: each wave sees short previews of all
completed prior waves.

## 8. The final assembled prompt (SYSTEM template)

`_SYSTEM_TEMPLATE` in `generator.py` is filled by `_build_system_prompt`:

```
You are a professional business analyst and technical writer.
You are generating the "{document_type}" document …

## PROJECT INFORMATION
- Project Name / Document Type / Target Audience / Stakeholders / Language

{ontology_block}                       # §6

## BUSINESS CONTEXT
{business_problem}                     # Project.problem_statement

## PROJECT DESCRIPTION
{project_description}                   # Project.proposed_solution

{additional_instructions_block}        # template style + extra project fields

## SOURCE DOCUMENT CONTENT
{llm_context}                          # §2/§4 — parsed docs + derived, capped 8k

{previous_sections_block}              # §7

--- FORMATTING RULES (Markdown, tables, target length {target_words}, language)
--- CONTENT QUALITY RULES (be specific, use Adani terms, prefer named AESL systems,
    NO placeholders like "TBD"/"[insert]", formal tone, output only the section)
```

The USER prompt (`_GENERATION_PROMPT`, §5a+5b) is concatenated:
```python
combined_prompt = f"{system_prompt}\n\n---\n\n{user_prompt}"
```

## 9. The LLM call

```python
# generator.generate_section
max_tok = _estimate_max_tokens(target_words)          # max(5000, min(target_words*6, 16000))
content, provider = call_with_fallback(
    messages   = [{"role": "user", "content": combined_prompt}],
    max_tokens = max_tok,
    timeout    = 180,
    log_prefix = f"[Generator:{section_key}]",
)
```

`call_with_fallback` (`llm_provider.py`) → `_call_gemini`:
- Model `vertex_ai/gemini-2.5-flash`, auth via `key.json` service account.
- **tenacity** retry: 3 attempts, exp-jitter, **only** on transient errors (429/5xx/timeout).
- Returns `(markdown_text, "gemini_vertex")`.
- (Extraction / derivation / persona-review calls set `json_mode=True`; section generation
  returns Markdown, so it does not.)

The section generator's `target_words` (from the Excel via `_spec_words`) drives
`max_tokens`, so length intent → token budget.

## 10. Two special paths

**Static sections (no LLM).** In `_generate_one`, if `cfg["mode"] == "static"`, the
`static_content` is inserted verbatim after `_fill_placeholders` substitutes
`{{project_name}}`, `{{nit_number}}`, etc. from `user_inputs`. Persisted as a normal
`SectionVersion` (`trigger_type="static"`). Used for NIT/RFP legal boilerplate — exact,
deterministic, zero tokens.

**Composite sections (one call for a parent + its sub-sections).** The compiler bundles
`4`, `4.1`, `4.2` … into one template section whose `instructions` embeds every
sub-section's write-instruction + boundary + columns (see `build_composite_instruction`
in `compile_mapping.py`). At generation time it is just one `generate_section` call that
returns the parent intro + `## 4.1`, `## 4.2` … headings. Fewer calls, same depth.

---

## 11. Short-table self-correction

After `generate_section`, `_generate_one` checks: if the section is a **table** and came
back **< 40 % of its target words**, it regenerates **once** with a stronger nudge
("output the FULL table with ALL rows…"). This is what fixed the BRD Functional
Requirements table (127 → 2 526 words). Composites (`render_hint="mixed"`) never trigger it.

---

## 12. Persistence

`_persist_section_version` writes a `SectionVersion` (v1) with `content`, the full
`generation_prompt` (for audit), `generation_model`, and **atomically** increments
`GenerationJob.completed_sections` (SQL expression, safe across wave workers). The stored
prompt is exactly what was sent — you can inspect any section's real prompt in the DB.

## 13. Worked example — BRD "Problem Statement" (Drishti)

1. `_load_job_context` builds Layer-1 context: the parsed `test_brd_drishti.docx` text
   (~4.3k chars, incl. its *"9. Proposed Solution Overview"*) + the 12 derived fields.
2. `generate_section` caps it to 8k (fits fully here).
3. USER prompt = *"Generate the Problem Statement section"* + the Excel Description
   ("State the core problems… From X → To Y… 4 short paragraphs") + guidance block
   (**MUST NOT INCLUDE: proposed solutions/tools** · Output format: Prose · Depth: …).
4. SYSTEM prompt = project info + **ontology** (AESL entity, matched glossary like SCADA/
   MERC) + BUSINESS CONTEXT (problem_statement) + PROJECT DESCRIPTION (proposed_solution)
   + SOURCE DOCUMENT CONTENT (the parsed doc) + previews of Purpose/Scope/Terms.
5. Gemini returns Markdown; short-table check skipped (prose); persisted as v1.
6. Validation later traces the output's salient tokens back to the source doc
   (provenance) — this project scored 91–100 with 13/13 fields grounded.

## 14. Quick reference — where to change what

| To change… | Edit | Then |
|---|---|---|
| What a section says / its length | `templates/<doc>.json` → section `instructions` / `target_words` | restart |
| A section's rules / exclusions | `templates/<doc>.json` → section `scope_boundary` | restart |
| Table columns | `templates/<doc>.json` → section `variables` (+ `format`:`Table`) | restart |
| Cover / template ID / classification | `mapping_data/template_config.json` | restart |
| Document-wide tone | `templates/<doc>.json` → `system_instructions` | restart |
| Universal formatting/quality rules | `generator.py` → `_SYSTEM_TEMPLATE` | restart |
| The spec block layout | `section_mapping.build_section_guidance` | restart |
| **How much source/derived context per section** | `generator.py` → `_MAX_CONTEXT_CHARS` (8 000) | restart |
| Per-doc/total source cap | `generation_service._load_job_context` (20k / 60k) | restart |
| Ontology grounding | `ontology/*.json` + `ontology.for_generation` | restart |
| Parallelism / speed | env `GENERATION_CONCURRENCY` | — |

See also `mapping_data/TUNING_GUIDE.md` for the non-code tuning workflow.
